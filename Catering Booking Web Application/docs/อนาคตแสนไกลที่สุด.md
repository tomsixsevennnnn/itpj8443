# เป้าหมาย

ตอนนี้ระบบเป็น **single-tenant** (ร้านเดียว — ร้านพิพัฒน์โภชนา) โครงสร้างข้อมูลทั้งหมดไม่มีคอนเซปต์ "ร้านไหน" เลย

เป้าหมายในอนาคต: ขายระบบนี้ให้เจ้าของร้านโต๊ะจีน/แคทเธอริ่งร้านอื่นทั่วไทยได้ แต่ละร้าน (ร้าน A, ร้าน B, ...) เข้ามาในฐานะ `owner` แล้วกรอก/แก้ไขข้อมูลร้านตัวเองได้ทั้งหมด (เมนู แพ็กเกจ ค่าตั้งค่า ราคา ฯลฯ) โดยที่ **ข้อมูลของแต่ละร้านไม่เชื่อมถึงกัน**

มี 3 แนวทางที่เป็นไปได้ สรุปไว้ทั้งหมด — ยังไม่ได้เลือกทางไหนแน่นอน

# แนวทาง 0: Manual — ทำได้เลยตอนนี้ ไม่ต้องแก้โค้ดสักบรรทัด

เพราะระบบเป็น single-tenant อยู่แล้วโดยธรรมชาติ การเอาโค้ดชุดเดียวกันไป deploy แยกกันคนละชุดให้ร้าน A กับร้าน B คือสิ่งที่ระบบรองรับอยู่แล้ว 100% ตั้งแต่แรก สิ่งที่ทำให้ข้อมูลแต่ละร้านไม่เชื่อมกันไม่ใช่โค้ด แต่คือการที่แต่ละร้านมี **DB คนละตัว + backend คนละ instance + Auth0 คนละ application** — ถ้าตั้งแยกกันจริง ข้อมูลก็แยกกันเองโดยอัตโนมัติ

## เช็คลิสต์ต่อร้าน (ของที่มีอยู่แล้วในโปรเจกต์ ไม่ต้องสร้างใหม่)

| ขั้นตอน | ใช้ของที่มีอยู่แล้ว |
|---|---|
| 1. สร้าง DB | `backend/docker-compose.yml` (dev local) หรือสร้าง Postgres instance บน Railway/ที่อื่น |
| 2. ตั้งค่า Auth0 | `docs/auth0-action.md` — สร้าง Application/API ใหม่ ผูก Action เดิม |
| 3. ตั้งค่า+deploy backend | `.env.example` เป็น checklist ตัวแปรที่ต้องกรอก แล้ว deploy |
| 4. รัน migration + seed | `prisma migrate deploy` + `prisma db seed` (คำสั่งพร้อมอยู่ใน `package.json`) |
| 5. ตั้งค่า+deploy frontend | `VITE_AUTH0_*` / `VITE_API_BASE_URL` แล้ว `vite build` deploy |
| 6. กรอกข้อมูลร้าน | เข้า role owner → หน้า "ตั้งค่า" กรอกทุกอย่างเอง (ชื่อร้าน ราคา เมนู แพ็กเกจ ฯลฯ) |

ขั้นตอน 1–5 ทำเองตามเช็คลิสต์นี้ได้เลยตอนนี้ — ต่างจากแนวทาง B (ด้านล่าง) แค่ตรงที่ **ไม่มีสคริปต์อัตโนมัติ** ต้องทำมือทีละขั้นทุกครั้งที่มีร้านใหม่ ถ้ายอมรับแรงงานตรงนี้ได้ ก็ไม่ต้องสร้างอะไรเพิ่มเลย — เริ่มขายได้ทันที

## ข้อดี/ข้อเสีย
- ✅ เริ่มได้ทันที วันนี้เลย ไม่ต้องพัฒนาอะไรเพิ่ม
- ✅ ความเสี่ยง data leak ข้ามร้าน = ศูนย์ (แยก DB จริงตั้งแต่แรก)
- ❌ ต้องทำมือทุกขั้นตอนทุกครั้งที่มีร้านใหม่ (เหนื่อยขึ้นเรื่อยๆ ตามจำนวนร้าน)
- ❌ ต้นทุน infra คูณตามจำนวนร้านเหมือนแนวทาง B

# แนวทาง A: Multi-tenant จริง (โค้ดเดียว ใช้ร่วมกันหลายร้าน)

การเปลี่ยนสถาปัตยกรรมใหญ่ ไม่ใช่แก้เพิ่มแบบ patch — แตะเกือบทุกชั้นของระบบ

## 1. Data model — เพิ่มแนวคิด "ร้าน" (Shop/Tenant)
- เพิ่ม model `Shop` ใหม่ (ชื่อร้าน, slug/subdomain, วันที่สมัคร, สถานะ)
- เพิ่ม `shopId` เป็น foreign key ในแทบทุกตารางที่มีอยู่: `Booking`, `Package`, `PackageCourse`, `MenuItem`, `BookingCounter`, `Settings`
- `Settings` จากที่ตอนนี้เป็น **แถวเดียวตายตัว (id=1)** ต้องเปลี่ยนเป็น 1 แถวต่อร้าน (`shopId` เป็น key แทน) — กระทบ `SettingsService` ทั้งไฟล์เพราะ hardcode `id: 1` ทุกจุด

## 2. Auth — รู้ว่า "owner คนนี้เป็นเจ้าของร้านไหน"
- Auth0 custom claim ตอนนี้บอกแค่ `customer`/`owner` ไม่รู้ว่าเป็นร้านไหน ต้องเพิ่มการผูก user ↔ shopId
- ต้องมี **ระบบสมัคร/สร้างร้านใหม่** (onboarding) — กรอกชื่อร้าน สร้างบัญชี owner คนแรกของร้านนั้น
- ต้องตัดสินใจ: ลูกค้า Google account เดียวจองได้หลายร้านไหม (ถ้าได้ ต้องมีตาราง "ลูกค้าคนนี้เกี่ยวกับร้านไหนบ้าง" แยกจาก user เดี่ยวๆ)

## 3. Backend — ทุก endpoint ต้อง scope ตามร้านเสมอ
- ทุก query ปัจจุบัน (`findMany` ไม่มี `where: {shopId}` เลยสักที่) ต้องแก้ให้กรองตามร้านของผู้ใช้ที่ login — พลาดจุดเดียวคือร้าน A เห็นข้อมูลร้าน B ได้ทันที (ช่องโหว่ร้ายแรง)
- endpoint สาธารณะอย่าง `/settings/public` ต้องรู้ว่าจะดึงข้อมูลร้านไหน (ต้องมี route แบบ `/shops/:slug/settings/public`)

## 4. Frontend — ต้องรู้ว่ากำลังเข้าเว็บร้านไหนตั้งแต่ก่อน login
- ต้องมีวิธีระบุร้าน เช่น subdomain (`ร้านเอ.yourapp.com`) หรือ path (`/r/ร้านเอ`)
- หน้า Login ต้องโหลดโลโก้/ชื่อร้านตาม shop context ก่อนแม้ยังไม่ login

## ข้อดี/ข้อเสีย
- ✅ ต้นทุน infra ใช้ร่วมกัน ไม่คูณตามจำนวนร้าน
- ✅ เพิ่มร้านใหม่ = แค่แถวข้อมูลใหม่ ไม่ต้อง deploy ใหม่
- ❌ พัฒนาซับซ้อนขึ้นมาก เสี่ยง bug ข้ามร้าน (data leak) สูงถ้าทำไม่รอบคอบ
- ❌ ใช้เวลาพัฒนานานกว่าแนวทาง B มาก

# แนวทาง B: แยก instance ต่อร้าน + Automate Provisioning

คง architecture เดิมทั้งหมด (โค้ดไม่ต้องแก้) แต่ละร้านมี DB + backend + frontend deploy แยกกันคนละชุด — ใช้สคริปต์อัตโนมัติแทนการตั้งค่ามือทุกครั้ง

## สิ่งที่ทำไม่ได้ผ่านหน้า Owner Settings (ต้องตั้งจาก env ก่อนแอปจะรันได้)
- `DATABASE_URL` — backend ต้องต่อ DB ให้ได้ก่อนจะ "รัน" ได้เลยด้วยซ้ำ
- `AUTH0_DOMAIN` / `AUTH0_AUDIENCE` (backend) — ใช้ตรวจ JWT ทุก request รวมถึง request ที่จะเปิดหน้า Settings เอง
- `VITE_AUTH0_DOMAIN` / `VITE_AUTH0_CLIENT_ID` / `VITE_AUTH0_AUDIENCE` / `VITE_API_BASE_URL` (frontend) — ถูกฝังเข้า JS bundle ตอน `vite build` เปลี่ยนตอน runtime ไม่ได้

สิ่งที่ทำได้อยู่แล้วผ่าน Owner Settings (เก็บใน DB จริง): ชื่อร้าน/ที่อยู่/เบอร์/บัญชีธนาคาร, อัตรามัดจำ, ค่าขนส่ง/โซน metro, ค่าแรงพนักงาน, เมนู, แพ็กเกจ, เนื้อหาหน้าแรก — แค่ต้องมี instance รันอยู่ก่อน (env ตั้งไว้แล้ว)

## ขั้นตอนที่ต้อง automate (เรียงตามลำดับที่พึ่งพากัน)

1. **สร้างฐานข้อมูล** — Railway API/CLI สร้าง Postgres instance ใหม่แยกต่อร้าน → ได้ `DATABASE_URL`
2. **สร้าง Auth0 Application ใหม่** — Auth0 Management API สร้าง Application + API (resource server) ใหม่ เปิด connection `google-oauth2` (ลูกค้า) + `Username-Password-Authentication` (owner) ผูก Action ตั้ง role claim (ตัวเดิม) เข้ากับ login flow ใหม่นี้ → ได้ `AUTH0_DOMAIN`, `AUTH0_AUDIENCE`, `client_id`
3. **Deploy backend** — Railway API สร้าง service ใหม่จาก repo เดิม ใส่ env vars จากขั้นตอน 1-2 รัน `prisma migrate deploy` + `prisma db seed` อัตโนมัติ → ได้ URL backend
4. **Deploy frontend** — Vercel API สร้าง project ใหม่จาก repo เดิม ใส่ `VITE_AUTH0_*` + `VITE_API_BASE_URL` (ต้องรู้ก่อน build)
5. **ปิดวง CORS** — ย้อนกลับไปอัปเดต `FRONTEND_ORIGIN` ของ backend ด้วย URL frontend ที่เพิ่งได้
6. **สร้างบัญชี owner คนแรก** — Auth0 Management API สร้าง user ใน connection username-password ของร้านนั้น ส่งอีเมลเชิญ/รหัสผ่านเริ่มต้น

## ข้อควรรู้ก่อนตัดสินใจทำ
- **ยังไม่ใช่ self-service** — สคริปต์นี้ต้องใช้ API key ระดับบัญชีของ Railway/Vercel/Auth0 (ของผู้ขาย ไม่ใช่ของร้าน) เจ้าของร้าน A/B กด provision เองไม่ได้ ต้องเป็นผู้ขาย (หรือระบบหลังบ้านที่ผู้ขายควบคุม) เป็นคนรันให้
- **ต้นทุนคูณตามจำนวนร้าน** — แต่ละร้าน = Postgres + backend service + frontend project แยกกันหมด ค่า hosting เพิ่มเป็นเส้นตรงตามจำนวนร้าน
- **Auth0 มีข้อจำกัดจำนวน tenant/application ตาม plan** — ถ้าจะขายหลายสิบ/ร้อยร้าน ต้องเช็ค pricing tier ให้รองรับ
- ใช้เวลา provision ต่อร้านราวๆ ไม่กี่นาที (รอ deploy build ทั้ง 2 ฝั่ง)

## ข้อดี/ข้อเสีย (เทียบกับแนวทาง A)
- ✅ ไม่ต้องแก้โค้ด/schema ของแอปหลักเลย ความเสี่ยง data leak ข้ามร้าน = ศูนย์ (แยก DB จริง)
- ✅ เริ่มทำได้เร็วกว่ามาก (เขียนแค่สคริปต์ provisioning ไม่ต้อง re-architect)
- ❌ ต้นทุน infra คูณตามจำนวนร้าน
- ❌ เพิ่มร้านใหม่ต้องรอ deploy (ไม่ใช่แค่ insert แถวข้อมูล)

# สถานะ

- **แนวทาง 0 (manual)** — ใช้ได้ทันทีตอนนี้โดยไม่ต้องพัฒนาอะไรเพิ่ม ถ้าจะเริ่มขายให้ร้านแรกๆ ทำตามเช็คลิสต์นี้ได้เลย
- **แนวทาง A / B** — ยังไม่ได้เลือก เก็บไว้เป็นไอเดียอนาคตสำหรับตอนที่จำนวนร้านเยอะขึ้นจนแรงงานมือใน "แนวทาง 0" ไม่ไหว ยังไม่มี timeline หรือ commitment ที่จะทำ
